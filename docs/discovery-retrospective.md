# Discovery redesign: evidence and limits

The missing-evidence problem spans discovery, extraction, submission projection and receiving validation. A successful inventory or accepted upload does not establish that identification clues survived.

## Retrospective evidence

- **DDPAI:** retained credential-free actual framing demonstrates root protocol JSON with model/software and component model/version fields, including ANSI logger decoration. This is replayable syntax evidence.
- **BlackVue:** prior extraction documentation records model declarations in version files and companion component-version information. That supports bounded text-like BIN discovery; it does not establish a universal binary decoder. Some documented model strings were explicitly expected/unconfirmed and remain so.
- **Viofo:** saved inventories establish the presence of configuration INI files. Those inventories alone do not prove retained setting values or supply a replayable configuration specimen.
- **Vantrue:** a retained allowlisted projection demonstrates menu-scoped labels and numeric values/flags for recording settings. Original assignment syntax was not retained in that projection. Custom menu-export enum interpretation remains an adapter/calibration task; the generic parser does not claim to understand every such export.
- **Historical derived reports:** 98 locally saved derived JSON records were checked for common support/config/version-file and protocol tokens; none contained those searched tokens. These are derived evidence records, not 98 independently validated physical cards or a complete audit of original private intake envelopes. Absence there must not be misrepresented as proof that the files were absent on cards.

## Implemented first layer

Both native implementations inspect bounded support candidates without requiring a known model or fixed manufacturer path. They retain typed technical declarations, source aliases, record context, format/encoding hints and explicit coverage. Unknown technical models can remain evidence without becoming catalog matches. Structured JSON, sectioned INI/key-value text, BOM-marked UTF-16 and supported framed JSON have synthetic regressions. The corpus is explicitly synthetic except where an actual sanitized framing is identified; no invented vendor grammar is presented as hardware validation.

Recognized support candidates precede ordinary media; unknown-file fallback remains. Large recordings and no-fact image entries must not consume all opportunity to discover a late configuration file. Tests cover those starvation cases. Model alternatives remain flagged even when detail retention is reduced.

Only validated technical values enter explicitly reviewed private submissions. Raw logs, arbitrary strings, GPS, credentials, identifiers, unknown parent keys and raw support paths are not uploaded. Source aliases are not original support filenames. Public exports strip private discovery recursively. Conservative value grammar can reject legitimate names or versions; it is not a universal semantic/privacy oracle, and review remains required.

## Not claimed complete

- No universal proprietary binary, XML, archive-payload, legacy-encoding or custom-menu decoder.
- No automatic identification merely from a generic model/version declaration, nor proof that it describes the main camera/current firmware.
- No full inspection of oversized or budget-excluded content; the gaps are counted.
- JSON location may be document-level (`line: 0`) rather than an exact field line; the UI says so. INI/framed locations remain positive source lines.
- No automatic network submission during scanning, and no restoration of the unsafe Scanner OCR worker.

The shared receiving validators are byte-identical and tested against both native implementations. Native-to-receiving-handler/storage tests are required in addition to parser tests. Packaged distribution and deployed-receiver acceptance remain separate from local source/test completion.
